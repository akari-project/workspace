目标：不含节点的完整商业闭环：注册、购买、续费、升降级、余额、优惠、通知、后台管理全部可用，可对外演示。

推荐组织方式：每个功能组一个 Agent Team（panel-backend + frontend + e2e-tester），前端在后端完成前使用 Mock 服务。

## M1-03b 设备授权与扫码登录 [待办]
- 仓库：panel（server、web/portal）
- 模式：团队（panel-backend、frontend）+ security-reviewer
- 依赖：M1-01（可与 M1-03 并行）
- 规格：spec/10 AUTH-23、AUTH-24，spec/30，spec/32（`/activate` 与扫码批准页均为 M1）
- 前置（开工前先经 spec-change 定案，未定前不写实现）：
  1. 存储：设备授权与扫码登录请求存放在 Valkey（带 TTL）还是数据库表；`user_code` 的存储方式。参考建议：`device_code`、`poll_token` 是令牌，按 CONV-20 只存 SHA-256。
  2. 限流：API-04 增加 `user_code` 输入的限流（RFC 8628 §5.1 防暴力猜测）；`approveDeviceLink` 校验数字“多次失败后作废”的次数。参考建议：候选数字只有 3 个，一次错误即作废。
  3. 路由与二维码：spec/32 定义扫码批准页的路由，AUTH-24 写明 `qr_content` 的生成规则与非 web 批准方解析 `id` 的方式；契约示例 `https://portal.example.invalid/link/{id}` 同步修改。参考建议：路由避开 `/link/`（与 API-02 列出的旧面板导入路径雷同）。
- 交付：
  - 设备授权（RFC 8628）：`POST /v1/oauth/device_authorization`（`startDeviceAuthorization`）、`POST /v1/oauth/token` 的 `device_code` grant、`POST /v1/me/device-authorizations`（`approveDeviceAuthorization`）；用户中心 `/activate` 页面（支持 `verification_uri_complete` 预填 `user_code`）。
  - 扫码登录：`POST /v1/device-links`（`createDeviceLink`）、`GET /v1/device-links/{id}`（`getDeviceLink`）、`POST /v1/device-links/{id}/approve`（`approveDeviceLink`），轮询复用 `/v1/oauth/token`（`poll_token` 作为 `device_code`）；用户中心扫码批准页（显示平台、型号、IP 前缀，地区有则显示，选择校验数字）。
- 验收：
  1. 两个批准接口未在 5 分钟内重新验证时返回 401 `mfa_required`（AUTH-23）；重新验证后用同一 `Idempotency-Key` 重试成功（CONV-12）。
  2. 两个批准接口返回 401 或 429 之前不写库，测试断言（CONV-12，M1-01 后续中的前置约束 S2）。
  3. `device_code` 轮询：批准前 `authorization_pending`，过快 `slow_down`，过期 `expired_token`（RFC 8628）；签发的令牌受众为 `client`；新设备计入设备上限，超限按 AUTH-14 以 `credential_status` 表达（计划阶段核实 `TokenPair` 的字段）。
  4. 扫码批准：`getDeviceLink` 返回 3 个候选数字；校验数字错误达到前置第 2 项定的次数后请求作废（`exhausted`）；非 web 批准方验证 `device_signature`（签名对象带 `akari-device-link-approval-v1` 前缀，AUTH-24），签名无效时拒绝；已批准或过期的请求返回 409 `invalid_state`。
  5. 被批准的新设备会话不写入重新验证状态（AUTH-23）。
  6. 端到端：用户中心完成 `/activate` 批准与扫码批准两条流程，新设备取得令牌。
