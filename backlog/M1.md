# M1 控制面核心与两端前端（6 周）

目标：不含节点的完整商业闭环：注册、购买、续费、升降级、余额、优惠、通知、后台管理全部可用，可对外演示。

推荐组织方式：每个功能组一个 Agent Team（panel-backend + frontend + e2e-tester），前端在后端完成前使用 Mock 服务。

## M1-01 账号与会话 [进行中 @claude/m0-xa70yn]
- 仓库：panel（server、web/portal）
- 模式：团队（panel-backend、frontend）+ security-reviewer
- 依赖：M0-05、M0-06
- 规格：spec/10、spec/32
- 交付：注册、邮箱验证、登录、刷新令牌轮换、登出、找回密码、TOTP、Passkey（可延后到 M4）；用户中心对应页面与“账号安全”
- 验收：
  1. 重复使用已轮换的刷新令牌吊销整条会话链。
  2. 登录失败与账号不存在返回相同错误与相近耗时。
  3. 未验证邮箱不能下单（`email_unverified`）。
  4. Playwright 覆盖注册、验证、登录、启用 TOTP。
- 范围说明（评审见 `review/m1-01-spec-gaps-2026-09-24.md`）：
  - 管理员生成的注册码（AUTH-02）移到 M1-07，与兑换码一起经 spec-change 补表与管理接口；M1-01 只支持账号邀请码，`invite_code` 的查找抽象为接口。
  - 注册时生成共用代理凭据并写 `credential.changed`（AUTH-13），登录时注册设备（AUTH-10），都在 M1-01 完成。
  - 为满足验收 4，先实现 M1-08 的最小投递路径：`Notifier`、`notification_outbox`（CONV-31）、无密码 SMTP（Mailpit）；重试退避、SMTP 密码与其余邮件仍在 M1-08。
  - 验收 3 的检查在本任务实现并测试，M1-06 下单时接入。
  - 先改 panel-spec：刷新令牌 Cookie 的描述与 AUTH-08 一致、`info.version` 与发布版本一致、`/v1/config` 增加可选 `registration_policy`。
